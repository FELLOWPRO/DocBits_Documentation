## 文档状态与状态条件

### 卡片：CONDITION\_DOC\_STATUS\_IS\_ISNOT / 文档状态检查

#### 用途

检查文档是否处于特定状态

#### 使用场景

* 审批前
* 工作流的特定阶段
* 基于状态进行路由

#### 文档状态类型

```
- Upload：正在上传
- OCR：正在扫描
- Classification：类型检测
- Ready for Validation：等待验证
- Workflow：处理中
- Pending Approval：需要审批
- Pending Second Approval：需要二次审批
- Auto Accounting：自动记账
- Export：正在导出
- Error：发生问题
```

#### 工作方式

```
当前状态: "Pending Approval"
    ↓
检查: 状态是否 = "Pending Approval"?
    ↓
是 → 继续执行操作
否 → 停止或执行其他操作
```

#### 示例

```
条件: "文档状态是否为 Pending Approval?"
    ↓
如果是: 创建审批任务
如果否: 执行其他操作
```

#### 参数

```
运算符: IS / IS NOT
状态: [选择状态]
```

## 日期与时间条件

### 卡片：CONDITION\_TIME\_IS\_ISNOT\_BETWEEN / 日期范围检查

#### 用途

检查日期是否介于两个日期之间

#### 工作方式

```
文档日期: 2025-10-23
    ↓
检查: 日期是否介于 2025-10-01 和 2025-10-31 之间?
    ↓
是 (十月) → 继续
否 (其他月份) → 停止
```

#### 计算

```
公式:
  开始日期 ≤ 文档日期 ≤ 结束日期?

示例:
  2025-01-01 ≤ 2025-10-23 ≤ 2025-10-31?
  是 ✅ 在范围内
```

#### 使用场景

* 检查日期是否处于财务期间
* 检查是否在截止日期范围内
* 检查是否在促销期内

#### 示例

```
条件: "文档日期是否介于十月 1 日和十月 31 日之间?"
    ↓
如果是: 十月发票 (按月处理)
如果否: 其他月份的发票
```

#### 参数

```
开始日期: [选择或输入]
结束日期: [选择或输入]
日期字段: [要检查的字段]
```

### 卡片：CONDITION\_CONTINUE\_CHANCE / 随机概率

#### 用途

按指定概率继续

#### 工作方式

```
概率: 50%
    ↓
掷骰子
    ↓
随机概率: 50% 是，50% 否
```

#### 使用场景

* A/B 测试工作流
* 抽样处理文档
* 随机质量检查

#### 示例

```
条件: "是否以 10% 的概率继续?"
    ↓
90% 的文档: 在此处停止
10% 的文档: 继续进行详细审核
```

#### 计算

```
如果概率 = 50%:
  - 50% 的文档继续
  - 50% 的文档停止

如果概率 = 10%:
  - 10% 继续 (每 10 份文档中 1 份)
  - 90% 停止
```

## 决策流示例

### 流程 1：基于状态的处理

```
文档到达
    ↓
检查: 状态 = "Ready for Validation"?
    ↓
是: 验证文档
    ↓
检查: 状态 = "Pending Approval"?
    ↓
是: 创建审批任务
    ↓
检查: 状态 = "Error"?
    ↓
是: 升级给经理处理
```

### 流程 2：基于供应商的处理

```
发票到达
    ↓
检查: 供应商状态是否为 ACTIVE?
    ↓
否: 阻止处理并升级处理
    ↓
是: 检查: 供应商是否为优选供应商?
    ↓
是: 快速审批
否: 标准审批
```

### 流程 3：基于金额并检查日期

```
发票到达
    ↓
检查: 金额 > €10,000?
    ↓
是: 检查: 日期是否在十月 (财政期间) 内?
    ↓
是: 分配给财务总监
否: 分配给财务经理
```

## 条件最佳实践

✅ **建议：**

* 使用具体的条件
* 使用样例测试逻辑
* 按逻辑顺序排列条件
* 为所有路径设置后备处理
* 记录复杂逻辑

❌ **避免：**

* 创建循环条件（A 依赖 B，B 又依赖 A）
* 让条件过于复杂
* 忽略边缘情况
* 假定字段始终有值
* 创建不可能成立的条件

### 采购订单导入触发示例

**配置：** 在“何时”下选择新采购订单导入事件 (`wf_new_purchase_order`) 并保留更新事件 (`wf_updated_purchase_order`) 未选中。为此独立于文档的工作流上下文配置后续操作。

**预期结果及反例：**新导入的采购订单触发的运行满足该条件。仅由更新触发的运行则不会。选择这两个事件允许任一事件。这会检查工作流触发器信息，而不检查发票当前是否包含采购订单编号。

这是一个说明性的测试配置和预期结果；它没有被执行。使用测试组织中配置的数据和收件人。

### 供应商状态变更触发示例

**配置：** 在“当”分组中选择运算符 `is`，再选择贵组织实际提供的一个目标状态。本例将其记作状态 A，另一个可用状态 B 不加入列表。

**预期结果及反例：**对于新状态为A的供应商状态变更事件，条件成立；对于新状态为 B 的事件，它为 false。使用运算符 `is not`，这些结果会反转。这是基于工作流程运行信息的事件触发器，而不是对发票上的供应商状态的一般检查。确认日志中的实际事件和所选状态。

这是一个说明性的测试配置和预期结果；它没有被执行。使用测试组织中配置的数据和收件人。
